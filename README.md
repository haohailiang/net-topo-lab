# net-topo-lab

多层网络拓扑的**分层懒加载**与**布局层解耦**演示。

React 18 + TypeScript + [AntV G6 5.x](https://g6.antv.antgroup.com/)，可跑在浏览器里，也能直接部署到静态托管。

---

## 这个项目想说明什么

大型网络管理产品里的拓扑动辄上万节点、五层以上结构（核心 → 汇聚 → 接入 → 楼层 → 终端）。传统实现是"打开就全量拉、全量算布局、全量画"，节点一多就卡到不可用。

这里用四个可交互的演示点，把优化前后的差别做成看得见、可复现的对比：

| 演示点 | 在页面上怎么验证 | 对应解决的问题 |
|---|---|---|
| **全量渲染 vs 分层懒加载** | 点「一键对比」，右下角给出同规模下的耗时与数据量倍数 | 首屏只需要核心与汇聚两层，其余按需下钻 |
| **布局层与图组件解耦** | 切「分层树 / 力导向 / 网格 / 环形」，图组件不重建，只替换布局层 | 换布局不再改业务代码，图组件可跨视图复用 |
| **逐层下钻 + 请求缓存** | 懒加载模式下点带 ▾ 的节点，看日志里的"命中缓存 / 回源"计数 | 同一层反复进出不重复请求 |
| **G6 4.x → 5.x 升级落地** | 本项目整体基于 G6 5.1 的 `setData` + `render` 异步模型 | 新版 API 下的布局、交互与性能写法 |

## 实测数据

本机（Windows、Chrome、常规笔记本）实测，页面右下角的数字就是真实 `performance.now()` 计时，不是写死的文案：

| 数据规模 | 节点 / 边 | 全量渲染 | 懒加载首屏 | 首屏数据传输量 | 数据量差 |
|---|---|---|---|---|---|
| 小 | 597 / 597 | 约 220 ms | 约 4 ms | 879 B | 约 130× |
| 中（默认） | 1801 / 1803 | 约 650 ms | 约 5 ms | 1.6 KB | 约 220× |
| 大 | 5249 / 5251 | 约 1.8 s | 约 7 ms | 1.6 KB | 约 640× |

几点说明，避免误读：

- 首屏耗时是**纯渲染**时间（`setData` + `render` 含布局），不含模拟的接口延迟（演示里每跳 45 ms）。
- 真正拉开差距的是**首屏数据量**：全量模式要把整棵树序列化后传给前端，懒加载只传"核心 + 汇聚"两层。节点越多，这个倍数越大 —— 这也是实际项目里卡顿的主因，而不是单纯的前端绘制慢。
- 表格数字会有波动，取决于机器负载与浏览器版本，以页面实测为准。

## 跑起来

```bash
npm install
npm run dev      # http://localhost:5180
```

其他命令：

```bash
npm run typecheck   # tsc --noEmit
npm run build       # 产物在 dist/，base 已设为 './'，可直接静态托管
npm run preview     # 本地预览构建产物
```

页面支持查询参数，方便直接分享某个结论的链接：

```
http://localhost:5180/?scale=L&autorun=full    # 直接跑大规模全量渲染
http://localhost:5180/?scale=S&autorun=lazy    # 直接跑小规模懒加载
```

`scripts/verify.mjs` 与 `scripts/snapshot.mjs` 用 puppeteer-core 驱动本机 Chrome，跑完对比并把截图落盘，用来做可复现的验证，不参与构建。

## 目录结构

```
src/
├─ data/topo.ts            # 合成拓扑生成（确定性 LCG 种子）、三档规模、mock 懒加载接口
├─ components/TopoGraph.tsx # G6 5.x 封装：渲染、换布局、清空、节点点击
├─ App.tsx                  # 面板、对比逻辑、下钻与指标统计
├─ index.css
└─ main.tsx
scripts/
├─ verify.mjs              # 真机跑全量 / 懒加载，读取真实计时
└─ snapshot.mjs            # 点「一键对比」后截图
```

数据模型是五个层级：

```
CORE（核心）
 └ AGG（汇聚）
    └ ACC（接入）
       └ FLR（楼层）
          └ PC（终端）
```

## 关于"从 40 秒到 3 秒"

原始项目里，多层拓扑下钻的现场感知是 40 秒以上降到 3 秒以内。那个数字来自更苛刻的条件：受限的客户端机器、带图标与多行文本和告警态的复杂节点样式、更深的层级与更复杂的链路关系，以及当时仍在用的 G6 4.x。

本 demo 用同一套方法在常规笔记本上跑合成数据，绝对耗时自然小得多（1.8 秒已经是"全量"侧的下限）。这里想证明的不是"我能把 40 秒变成 3 秒"这句结论，而是**这套优化的每一环都可以被量化验证**：首屏数据量降了三个数量级，渲染耗时随之下降，下钻有缓存兜底，换布局不用重写图组件。

## 可以继续做的方向

- `backend/`：Spring Boot 3 + Caffeine 的真实懒加载接口（`/api/topo/children?parentId=&depth=`），与前端 mock 保持同一份契约，用于本地 `docker compose up` 演示。
- 节点样式升级为带图标、状态色与多行标签的卡片式节点，观察复杂样式下的性能差异。
- 增量渲染：下钻时只 append 新节点，不重算全图布局。
- 大规模下的虚拟化与聚合渲染（同一层超过阈值时折叠为聚合节点）。
