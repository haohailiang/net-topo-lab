# net-topo-lab · 多层网络拓扑下钻演示

一个用 **Vue 3 + TypeScript + G6 5.x** 写的四层网络拓扑下钻演示，用来复现"大型网管里拓扑下钻慢、点不动"这类工程问题的解法。

**在线演示**：https://haohailiang.github.io/net-topo-lab/ （点第 1 层的 `＋` 热区或虚线域框，一层层往下钻）

> **数据全部是合成的。** 仓库里没有真实拓扑、没有客户名、没有设备型号、没有公司代码片段、没有内部接口定义。节点名是 `NE-01-02` 这样的编号，链路叫 `TRUNK-01`、`SEG-1-1`，告警是随机生成的。这里公开的是**方法与结构**，不是业务数据。

---

## 它想说明什么

原项目是多层网络拓扑：一个产品线上百人协作，拓扑要同时满足"看全局"和"钻到单板"两种需求。老的实现把整棵树一次拉下来、一次画完，结果是首屏几秒、下钻一次四十秒往上。

这个 demo 用一份结构等价、量级相近的合成数据，把当时拆开的几件事重新做了一遍，每件事都能在界面上单独验证。

---

## 页面结构

固定四层，**纵向堆叠、每层一张独立的图**，不是往下换图——第 1 层始终留在屏幕上，第 2/3/4 层依次在它下面新开一张。每层高度固定 340px，四层叠加超出就整页滚动。

| 层 | 内容 | 怎么进来 |
|---|---|---|
| 第 1 层 | 主干拓扑：一排主干网元，相邻两点之间一条被抽掉的抽象链路 | 默认 |
| 第 2 层 | 点链路：这条被抽掉的链路内部——两端网元 + 中间的中继设备与子链路 | 点链路 / 点域 |
| 第 3 层 | 再往里一层同样的展开 | 点链路 / 点域 |
| 第 4 层 | 单板层：第 3 层**全部网元与全部端口**展开成单板，含单板间 CTP 连接 | 第 3 层头部的「详情 · 全部网元单板」 |

第 4 层的入口是**整层一个全局按钮**，不是每个网元各一个 —— 因为它展开的是整个第 3 层的单板，一张图里 990 块板。

---

## 两种下钻入口

- **点链路**：链路中点有个小圆点热区（`＋`）。链路下钻 = 展开这条被抽象掉的链路。
- **点域**：域由后端预先分组，固定两个网元，用户不能手动框选。

点同层的另一条链路，这一层被顶替，**它下面挂着的所有层整棵销毁**。

---

## 告警模型

业务上是四类，渲染上是三类：

| 类型 | 落在哪 |
|---|---|
| 网元告警 `ne` | 节点 |
| 端口告警 `port` | 节点 + 链路 |
| 单板告警 `board` | 只在第 4 层，向上只到所属网元 |
| CTP 告警 `ctp` | 第 4 层的"端口级"，向上落网元 + 端口两处 |

- 三级颜色：一级 `#e5484d` > 二级 `#f28b30` > 三级 `#e3b505`。
- 节点颜色取该节点上**最高**级别；角标数字取**全部级别累加、按告警对象去重**的总数。
- 单板告警数 = 1 时，顶层网元只计 1，不重复累加同一对象。

单板层刻意**不参与上层角标汇总**：它是整层共用的，如果算进每个网元的角标，同一批 990 块板的告警会在 11 个网元里各算一遍，数字虚高到没有意义。所以第 4 层的告警只在它自己那张图上落色和数角标。

## 前后端各做了哪些优化

界面上每一项都能单独触发并看到数字变化。

**后端**

- 旧：Node 单线程同步，一层里 3 条可下钻链路**顺序**请求。
- 新：Java 微服务 + 线程池，3 条链路**同时**处理再 reduce 合并。
- demo 里用 `setQueryCost()` 模拟每次子查询 15ms：同一棵子树串行 **158ms / 10 次查询**，并行 **31ms / 10 次查询**。左栏「一键对比串行 / 并行」就是跑这个。

**前端**

1. **缓存**：下钻结果短时间内不变，同一路径直接命中缓存。
2. **空闲预取**：页面空闲时用 `requestIdleCallback` 分批（每批 3 条）把当前拓扑的子路径提前拉到前端缓存。点下钻时如果缓存已就绪，直接命中。
3. **降级**：缓存没就绪时点下钻仍走小请求，只拉需要的子树，不阻塞。
4. **请求中断**：点第二条链路时立刻 `AbortController.abort()` 掉第一条还在飞的请求，并用请求令牌丢弃过期结果。旧实现不取消不销毁，旧结果回来会把新图覆盖掉。
5. **刷新只失效本层**：头部的「刷新本层」只让当前这一层缓存过期，父层、子层都不受影响。

## 布局

这一层的形状不是"网状"，是**条状**：A 点到 B 点之间并行 2~3 条路径（主 / 备 1 / 备 2），聚焦的是两点之间的关系。G6 内置的 dagre / force / grid / radial 摆出来都不能看，所以业务布局是自定义的：

| 布局 | 用在哪 | 摆法 |
|---|---|---|
| 主干链 `chain` | 第 1 层 | 主干网元横排，相邻连线 |
| 三走廊 `corridor` | 第 2/3 层 | 左右两端点 + 中间三条并行走廊，按路径分带 |
| 单板矩阵 `matrix` | 第 4 层 | 按所属网元分块，块内网格密排，间距按像素写死 |
| 星辐 `star` | 备用 | 中心节点 + 环绕 |

界面上还留着 dagre / force / grid / radial 四个 chip，**标注「内置，仅作对照」**——它们只是证明"默认布局不够用"，不是可选方案。

三走廊的实际业务比这复杂得多，这里按"示意"处理：两端点 + 三条路径，够表达结构。

## LOD 三档

990 块板全显示，靠缩放分层，**不重画图**，只在缩放跨阈值时批量改样式：

- **档 0**（全览）：只画小点、按告警着色，不显示名称，CTP 退化成淡色细线。
- **档 1**：点变大，显示单板编号。
- **档 2**（放大）：显示单板名 + 端口 + CTP + 告警角标。

判档用的是**相对初始缩放**而不是绝对 zoom：第 4 层 fitView 之后 zoom 已经是"全览"了，再用绝对阈值判档等于永远在档 2。稀疏的层级（6~11 个网元）则相反——全览就该看到名字，只有缩得很小才退成小点。

## 联动高亮

单向，从上往下：

- 第 1 层点了 `TRUNK-01`，下钻到第 2 层时，第 1 层的 `TRUNK-01` 高亮（点的是域就高亮域）。
- 第 1 层再点第 2 条链路 → 新的高亮，旧的恢复默认。
- 下层点击不回传上层：上层固定，下层不需要动。
- 每层头部显示来源路径（面包屑）：`主干拓扑 › TRUNK-01 › SEG-1-1 › 整层全部单板`。

## 技术栈与运行

```bash
npm install
npm run dev        # http://localhost:5180
npm run typecheck  # vue-tsc --noEmit
npm run build      # 产物可直接静态托管（base './'）
```

Vue 3 `<script setup>` + TypeScript + G6 5.1.x，无后端依赖，`build` 出来丢到任何静态托管都能跑。

规模切换：左栏 `小 / 中 / 大` 三档，第 4 层单板总数分别是 204 / 990 / 994，都卡在 1000 以内。

## 验证脚本

不是点一遍看看，是四个能复跑的脚本：

```bash
node scripts/check-data.mjs   # 直跑数据层：逐层结构、第4层单板数与 CTP 分项、串行 vs 并行、三档规模

node scripts/check-flow.mjs   # 四层全链路：点链路 → 点链路 → 点详情，校验每层节点链路数与面包屑
node scripts/check-lod.mjs    # 第4层滚动放大，校验 LOD 档位切换
```


## 目录

```
src/
  data/
    model.ts        四层模型与告警类型的唯一真源
    generate.ts     合成数据生成器（主干链 / 三走廊 / 单板层）+ 拓扑缓存
    alarms.ts       告警生成、递归汇总、去重
    server.ts       mock 接口：缓存、中断、预取
  components/
    TopoGraph.vue   G6 封装：域框、热区、事件、LOD、高亮
    layouts/        四个自定义布局（纯函数，与图组件解耦）
  App.vue           视图栈：下钻、中断、刷新、预取、串并行对比
```

**布局层与图组件解耦**是这套结构的关键：布局只接收 `{ topo, width, height }` 返回坐标，不认识 G6；图组件只管画和交互。加一种新布局不用碰图组件，这也是原项目里代码量能降到 1/6 的原因之一。

## 和原项目的差别

- 原项目是真实的 Java 后端 + 前端，这里**不跑后端**：`server.ts` 用一个可设延迟的 mock 把"每次子查询 15ms""顺序 vs 并发"这些行为模拟出来，真实实现逻辑写在这里。
- 原项目四层各自的数据结构、接口、缓存策略都在服务端有对应实现，这里只保留前端能演示的部分。
- 40 秒 → 3 秒是**原项目的真实数据**；本 demo 里能复现的是同一套拆解思路在小数据量上的比例关系（比如串并行 158ms vs 31ms），两者不是同一个数。
